HLS → LLS → RTL tape-out → chip arrives → FW starts ← here → DV starts ← here

LLS was a verification artifact owned by DV — built after RTL exists, always late. FW and DV waited. Chip arrived, discovery began: register mismatches, interrupt timing wrong, DMA burst behavior undocumented. Each finding risks a respin.

Before any RTL or SystemC is written, the team develops to micro-architecture level in YAML: state machines, register maps, pipeline stages, interrupt behavior, DMA protocols, timing constraints. More precise than English spec, less detailed than RTL. One source fans out to all artifacts — consistency guaranteed by construction, not by cross-team review.

Architecture Methodology — How a Principal Engineer Approaches SoC Design

A rigorous 6G RU/DU SoC architecture process follows a specific sequence. Each phase has known optimism/pessimism biases — understanding those biases is what separates a principal architect from someone reading a datasheet. The sections in this document follow this sequence exactly.

01
Product Envelope
Define what you are building: target band, UE/CC count, throughput, power, form factor. Ground in a reference platform (Company-A DU100) and the 6G aNB target delta.
Bias: sets the design point — get this wrong and everything downstream is wrong
02
Static Latency Analysis
Single CC/UE pipeline: ChEst → MIMO EQ → LDPC decode → ACK. Measures how long the critical path takes with dedicated resources. No contention modeled.
⚠ Over-optimistic — dedicated resources don't exist when 4 CC run simultaneously
03
Static Peak Analysis
Worst-case simultaneous load: all UE/CC at peak, all tasks at max duration. Sizes coprocessor counts (LDPC engines, CE lanes, MIMO lanes) from first principles. The classic "static Excel" approach.
⚠ Over-pessimistic — worst case across all resources rarely happens simultaneously
04
Contention Simulation
SimPy discrete-event model: realistic concurrent load across all paths, priority queuing, stochastic task durations. Closes both gaps — finds true P99 latency under real contention.
Corrects both biases — some paths worse than static, some better
05
DVFS Analysis
Accelerator config → Fmin that meets 5–10% margin → voltage from DVFS curve → power reduction estimate. Validates frequency scaling is safe before committing silicon.
06
Architecture Decisions
Simulation findings drive architecture: VU count, program SRAM topology, HRTC/PRE partition, process node selection. Area analysis validates feasibility at N3E.
Grounded in simulation evidence, not intuition
Why static analysis alone is insufficient
Static latency (Step 2) assumes dedicated resources. In a 4-CC system, 4 ChEst jobs launch simultaneously and compete for 8 CE lanes — P99 latency is 20-30% higher than the single-path estimate.

Static peak (Step 3) assumes worst case on every dimension at once. The DL scheduler appears to fail (278µs > 250µs budget) — but simulation reveals this is a priority-blocking artifact, not a capacity problem. GPU offload of the AI scheduler removes it from HRTC resource competition entirely.
Why simulation is the starting point, not the end
The sim_v18 model covers 28 of ~200 RISC cores (8 CE + 4 MIMO + 4 risc_ctrl + 12 risc_sched) and the 4 HRTC paths. It is intentionally scoped — modeling every subsystem produces noise, not signal.

The output is not a pass/fail verdict but a set of architectural questions: where is margin tight, where is priority the real constraint, where does GPU offload buy the most headroom. Those questions drive Steps 3–5.

Key Findings
FINDING 01
The appeal of two-layer architecture

Layer 1 (HRT): RISC + TCM + coprocessors, hard deadlines. Layer 2 (PRE): GPU + AI, runs 1–2 slots ahead, soft deadlines. Mixing them: cache non-determinism bleeds into HRT — P99/P50 grows from 1.4× (pure TCM) to 2.8× (GPU on HRT path). Layer 2 must never call into Layer 1 in real time.

FINDING 02
PDCCH is not the tightest path — scheduler is

72% of DCI fields are pre-computable 1–2 slots ahead. Last-mile UE-dependent patch (HARQ ID + NDI + MCS ≈ 12 bits) takes ~1.2µs — trivially fits any budget. The bottleneck is the scheduler: RISC PF needs 2,576µs at 32UE 4CC vs 500µs PRE window.

FINDING 03
FR1 needs very little · FR2 needs a few

FR1 macro passes with only LDPC decode + bit-processing + polar. FR2 mmWave (80% SPS) additionally needs PUCCH F0 detector and PRB/VRB mapping. Just 4–5 of 9 knobs meet FR2 requirements. Company-A's full IP suite reflects modem IP reuse, not engineering necessity.

FINDING 04
AI Scheduler in 6G FR3/FR2
FR3 = 7–24 GHz upper mid-band (primary 6G band, between FR1 & FR2 in frequency) · FR2 = ≥24.25 GHz mmWave · FR# order ≠ frequency order

At 32UE 4CC µ=2: ALL Layer 1 knobs combined fail at 80% PDCCH miss. AI scheduler (GPU, O(CC^0.4)) drops scheduler from 2,576µs to 92µs. Deployable NOW — proprietary gNB software, no 3GPP standardization needed.

FINDING 05
LDPC decode is the PUSCH bottleneck

PUSCH LDPC decode P99 at µ=2 K1=2: 432µs with HW engine vs 6,914µs pure SW — 16× difference. Highest single-knob impact. At K1=1 URLLC (125µs budget) even the HW engine fails — genuinely unsolved problem. PUCCH F0 ZC detector (2 dot products) adds <1µs with coprocessor — critical for µ=3 HARQ turnaround.

FINDING 06
Bit processing: pervasive 4× gain across pipeline

CPU is slow at bit operations: DCI packing, RB bitmap, false alarm LLR metric. Generic bit-processing custom instructions: ~4× improvement pervasively. Coprocessors: ~10×. Conservative 1/4× estimate used throughout. Confirmed present in Company-A DU100 (modem IP reuse).

FINDING 07
3GPP confirmed the DCI bottleneck independently

Legacy per-CC DCI (Rel-15/16/17) scales O(N_CC) — our identified bottleneck. 3GPP response: Rel-18 introduced DCI Format 1_3/0_3 (single DCI scheduling multiple CCs). Rel-19 extended to mixed SCS. 6G Rel-20 studies a super carrier (400MHz single CC, one PDCCH, zero per-CC overhead) — prototyped at MWC 2026 by Ericsson + Company-A.

Why RF power-up lead time is not in this pipeline On the UE side, RF power-up is a real constraint: depending on RRC state, the UE RF chain may be fully powered down (RRC_IDLE) or in low-power standby (DRX), requiring 75–270µs for PLL lock, register programming via MIPI RFFE, PA ramp and settle before the first TX symbol. This is why 3GPP K2 minimums are UE-capability-gated.

At the macro gNB / 6G aNB the situation is fundamentally different: RF is continuously powered during TDD operation. The 64T64R (or 256T256R) PA array is always biased at quiescent point — only the output stage is TDD-gated (~<1µs transition), not powered down. Fully digital beamforming means W matrix weights are applied in the digital baseband before the DAC — no analog phase shifter settle time. The closest gNB analog to UE RF lead time is the O-RAN eCPRI fronthaul T12/T34 timing: the DU must deliver C-plane resource allocation to the RU at least ~250µs before the UL slot. This is already what our PDCCH scheduling deadline (285µs budget) is designed to meet — it is embedded in the pipeline budgets shown above, not a separate overhead.

Exception: hybrid analog/digital beamforming (legacy RRH with SPI-programmed phase shifters) does add 50–200µs settle overhead per beam change. This is why 6G aNB targets fully digital massive MIMO — eliminating analog settle latency entirely and making sub-slot scheduling feasible.
PUSCH additional DMRS (sym 10/11) — the real HRTC timeline constraint Like PDSCH, PUSCH supports additional DMRS at late symbols to combat high Doppler (TS 38.211 Table 6.4.1.1.3-3/4, dmrs-AdditionalPosition: pos0/pos1/pos2/pos3). With double-symbol additional DMRS at l0=2, positions land at symbols 7 and 11. At µ=3 (125µs slot), symbol 11 arrives at 11 × 8.93µs = 98.2µs into the slot.

Impact on effective processing window: The gNB must wait for the symbol 11 DMRS before completing channel re-estimation. ChEst takes ~90µs after last DMRS received → completes at 98.2 + 90 = 188µs. Slot boundary is at 125µs, so LDPC cannot start until ~188µs into the processing budget. Effective processing window shrinks:
  • Without additional DMRS (pos0): ~375µs available after slot boundary
  • With additional DMRS at sym 11 (pos2): ~285µs effective window

Impact on GPU LDPC crossover: At 375µs window: GPU passes up to 512 CBs (2 batches × 150µs = 300µs ✓). At 285µs window: GPU 2-batch LDPC (300µs) + HARQ chain (30µs) = 330µs > 285µs ✗ fails. Single batch (≤256 CBs, 150µs) still passes. Company-A DU100 hardwired: 15µs/CB — unaffected in either window.

AI scheduler cross-layer opportunity: The gNB scheduler controls dmrs-AdditionalPosition per UE via RRC. MRSS — Multi-Radio Spectrum Sharing: The 5G→6G Deployment Reality
What MRSS is (3GPP Rel-20 study, MRSS = Multi-Radio Access Technology Spectrum Sharing):
  The 5G→6G transition will not be a hard cutover — operators will run NR and 6G aNB
  on the SAME frequency band simultaneously for years, exactly as LTE+NR DSS ran 2019–2024.
  
  FR frequency note (important — naming is NOT in frequency order):
    FR1: ≤7.125 GHz        (sub-6 GHz, wide coverage, came first)
    FR3: 7.125–24.25 GHz   (upper mid-band, "golden band" for 6G — sits BETWEEN FR1 and FR2)
    FR2: ≥24.25 GHz        (mmWave, high bandwidth, came second — higher freq than FR3)
    FR# numbers follow specification timeline, NOT frequency order.
    FR3 < FR2 in frequency despite FR3 > FR2 in number.
  
  Key design decisions already confirmed in 3GPP (as of 2026):
    - 6G aNB uses the same OFDM waveform and numerology as 5G NR
    - Subcarriers are aligned between NR and 6G on a shared carrier
    - This eliminates the CRS collision problem that made LTE-NR DSS painful
    - Dynamic scheduling + semi-static reserved resources share one carrier
    - 6G avoids NR SSB / NB-IoT / LTE-M reference signal resources semi-statically
    
  TDD slot allocation in MRSS:
    Some slots → NR UEs (existing 5G devices)
    Some slots → 6G aNB UEs (new 6G devices)
    Both on the same physical carrier, same site, shared RU
    The DU must jointly schedule NR and 6G UE populations
    without inter-RAT collision on PDCCH, reference signals, or data channels

Why MRSS strengthens the GPU argument:

  1. Joint NR+6G scheduler — exactly what GPU AI handles natively:
     A rule-based RISC scheduler would need:
       Separate NR scheduler + separate 6G scheduler
       + a coordination layer to prevent collision
       + priority arbitration when NR and 6G demand the same slots
     This is three software layers where one previously existed.
     
     A GPU AI scheduler sees both NR and 6G UE populations as one
     heterogeneous input tensor — the neural network learns the
     joint allocation policy across both RATs without explicit rules.
     MRSS is precisely the use case that makes the AI scheduler
     not just "faster" but architecturally necessary.

  2. Dual LDPC code family — exactly what GPU software handles:
     NR UEs:  LDPC BG1/BG2 (5G NR, current standard)
     6G UEs:  potentially new LDPC variant (Rel-20 study on
              enhancement beyond 5G NR range)
     The DU must decode BOTH simultaneously in the same HRTC window.

     Company-A DU100 hardwired: BG1/BG2 fixed in RTL — cannot handle new variant

     MRSS makes the channel coding upgradability argument CONCRETE:
     it's not a hypothetical future scenario — it's the required
     deployment mode during the NR→6G transition period (2030–2035).

  3. Deployment timeline implication for Company-B SoC:
     A 6G RU/DU SoC shipping in 2028–2029 must support MRSS on day one.

aNB LDPC Architecture — Why Many Narrow Engines, Not One Wide
Key insight (from hardware experience): aNB LDPC ≠ UE LDPC

UE LDPC decoder (optimized for single-CB throughput):
  Goal: decode ONE large CB as fast as possible
  Design: one or two WIDE decoders (384-wide layered min-sum or wider)
  Peak: ~8 Gbps on BG1 large CBs (8448 bits)
  Small-CB problem: when CB drops to 500 bits, the 384-wide decoder
    has ~94% of its check-node parallelism sitting idle on padding
    Effective throughput collapses to ~0.5 Gbps — the peak spec is
    meaningless in this regime

aNB / gNB LDPC decoder (optimized for CB concurrency):
  Goal: decode MANY different CBs simultaneously within the HARQ deadline
  Design: MANY NARROW engines, each handling ONE CB from ONE UE
  Typical UL CB mix at aNB:
    Edge UEs (QPSK, low SNR): 100–800 bits (BG2, small lifting)
    Mid-cell UEs (16QAM):     1,000–3,000 bits
    Peak-rate UEs (256QAM):   3,000–8,448 bits (BG1)
  aNB narrow engine on a 500-bit CB:
    Simpler pipeline, ~5-8µs per CB (vs 15µs for large-CB UE engine)
    Because: fewer check nodes, fewer lifting layers, shorter pipeline fill
  True parallelism: 16 UEs × 4CC × 8 CB each = 512 simultaneous CBs
    → need 512 engine-instances
    → you CANNOT reuse one engine's idle parallelism across different UEs'
      CBs — different RNTI, different HARQ process, different code params

Minimum engine count — deployment envelope dependent:
  Formula (from simulation):
    N_engines = ceil(N_UE × N_CC × N_CB × hw_us / deadline × safety_margin)

  Illustrative operating points:
    Very small cell (2 UE × 2CC × 1 CB, light load): ~4 engines
    Small cell     (4 UE × 2CC × 4 CB, moderate):    ~8 engines
    Macro aNB      (8 UE × 4CC × 8 CB, HARQ ET):    ~32 engines
    Dense macro    (16UE × 8CC × 8 CB, HARQ ET):    ~128 engines

  The right number depends on the carrier's traffic envelope and
  deployment scenario — 4-8 engines is the right range.
  4 engines handles FR1 eMBB comfortably (K1=1, µ=1 → 500µs deadline is generous).
  8 engines is needed when URLLC UEs run µ=3 (125µs deadline) on the same card —
  serial decode of all CBs exceeds budget at that point.
  Area cost is negligible (~0.1mm² each at 5nm). Actual floor depends on
  carrier input (UE density, CC count, URLLC mix, K1 configuration).
  
  What is clear:
  → Being stingy on tiny LDPC engines while paying GPU cycles is
    the wrong tradeoff regardless of the exact floor number.
  → Each narrow LDPC engine: ~0.1mm² at 5nm.
  → Equivalent GPU SM doing the same work: ~1.5mm², 5-10W.
  → The economics argument holds whether the floor is 4 or 8.

DVFS Validation Methodology:

  1. Add accelerators → measure P99 reduction at Fmax (400MHz)
  2. Compute margin = (budget − P99) / budget
  3. Find Fmin: P99(F) ≈ P99(Fmax) × Fmax/F  [latency ∝ 1/F]
     Solve: budget × (1 − target_margin) = P99(Fmax) × Fmax / Fmin
     → Fmin = P99(Fmax) × Fmax / (budget × (1 − target_margin))
  Fmax = 1GHz at 0.75V (N3E nominal); Fmin floor = 200MHz at 0.55V
  4. DVFS voltage curve (N3E typical):
     V(F) = Vmin + (Vmax − Vmin) × ((F − Fmin) / (Fmax − Fmin))^α
     where Vmin≈0.55V, Vmax≈0.75V, α≈0.6 (sub-linear, N3E modem typical)
  5. Power model:
     P_dynamic ∝ C × V² × F   (scales as V²F)
     P_leakage ∝ V^3           (dominant at N3E, strong V dependence)
     P_total = P_dyn + P_leak  (normalized to Fmax baseline = 1.0)

  Key insight: at N3E, leakage power has strong voltage dependence (V^3).
  Even modest voltage reduction from DVFS yields disproportionate leakage savings.
  This is why accelerator investment pays back in power — not just through
  frequency reduction but through the voltage headroom it creates.
Step 5a — Architecture Decision: VU Time-Share vs Dedicated at TSMC N3E

Three architectures. The baseband pipeline uses Nsub replicated subsystems (4–6), each handling an independent UE/CC partition. A — Distributed, dedicated VU: each subsystem has dedicated VUs; programs are distributed (128KB each, local to their subsystem). Simple, no sharing. B — Distributed, time-share VU: each instance carries one 461KB combined program, 4 VUs time-shared across CE/MIMO/Spare. Fewer VUs, more SRAM. C — Consolidated, time-share VU: one central 384KB program shared by all instances via bus. VUs time-shared globally across instances (4VU+4RISC per subsystem). Fewest VUs AND one program copy. Tradeoff: instruction fetch latency may increase ~2× under contention, but VU programs are typically branch-free deep loops — a prefetch buffer hides most of the latency. With realistic 200KB programs, SRAM dominates (~92% of area). Shared program eliminates the Nsub multiplication, saving 65–73% of total subsystem area at Nsub=4–6.

Step 5b — Architecture Decision: O-RAN Functional Partition (HRTC / PRE)

O-RAN's split 7.2x divides PHY into High-PHY (O-DU) and Low-PHY (O-RU). Within the O-DU, a further internal split — O-DU Low vs O-DU High — creates the partition that matters most for silicon architecture: hard real-time HRTC functions vs schedulable PRE functions. This appendix documents the architectural case for co-locating O-DU Low with the RU as a custom ASIC, leaving the GPU to handle O-DU High/PRE where its scheduling jitter is harmless.

APPENDIX — Multi-CC LDPC
Multi-CC LDPC: 4 parallel engines is optimal

Wait-for-all: gNB cannot advance scheduling until ALL CC PUSCH decodes complete. 4 parallel LDPC engines: 8CC P99 grows only 1.16× vs 1CC (two batches of 4). Serial (1 engine): 4.54× — catastrophic. More than 4 engines: diminishing silicon returns.

APPENDIX — SRS Mixed-µ
SRS mixed-µ: gNB analog of UE TX-priority problem

When µ=1+µ=2+µ=3 SRS arrive simultaneously, gNB must process µ=3 first (250µs hard deadline, SRS takes 213µs). Company-A DU100: 7.9% miss rate (simulation, 3000 runs). Company-B GPU-PHY: handles SRS in GPU compute — no dedicated HW. Exact miss rate unconfirmed (earlier "17.9%" figure was based on a fabricated DPU engine speed assumption; retracted in v15). SRS staggering (1 UE/slot) is mandatory for both architectures.
